# Changelog

## Unreleased

### New features

* **PostgreSQL support.** Added `DatabaseType.POSTGRESQL`, `PostgreSqlConnection` and `DatabaseConfiguration.createPostgreSql(...)`. `HikariDatabaseConnection` works with PostgreSQL too. Add the `org.postgresql:postgresql` driver to your plugin.
  * Sarah still writes identifiers between backticks. For PostgreSQL they become double quotes before the statement is sent; text inside `'...'` is not touched. Quoted names are case-sensitive in PostgreSQL, so use a column in the same case everywhere.
  * Types are mapped to their PostgreSQL equivalent: `LONGTEXT` → `TEXT`, `BLOB` → `BYTEA`, `ENUM(...)` → `VARCHAR(255)`, auto-increment → `GENERATED BY DEFAULT AS IDENTITY`.
  * `updated_at` from `timestamps()` defaults to `CURRENT_TIMESTAMP` but is not updated automatically on change, since PostgreSQL has no `ON UPDATE`.
* **Dialects.** The differences between engines moved to `fr.maxlego08.sarah.dialect` (`MySqlDialect`, `MariaDbDialect`, `SqliteDialect`, `PostgreSqlDialect`), available through `DatabaseConfiguration#getDialect()`. `DatabaseConfiguration#prepare(sql)` replaces `%prefix%` and adapts a statement for the configured engine.
* **Atomic increments.** `Schema#increment(column, amount)` adds to a value instead of replacing it:
  * update: `col = col + ?`
  * upsert: inserts the amount into a new row, adds it to the existing value otherwise, in one statement. Two servers adding at the same time no longer overwrite each other.
  * insert: writes the amount as is.
* **Expressions.** `Schema#expression(column, sql, params...)` assigns raw SQL to a column, for example `` `version` + 1 `` or `CURRENT_TIMESTAMP`. On an upsert it only applies when the row already exists.
* **Insert-only columns.** `Schema#insertOnly()` keeps the existing value of the last column when an upsert finds the row, for example a creation date. An upsert where every column is insert-only does nothing on conflict.
* **More conditions.** `Schema#whereNotIn`, `#whereBetween`, `#whereNotBetween`, `#whereLike` and `#whereNotLike`, on selects, counts, updates and deletes. `BETWEEN` includes both bounds, and its bounds keep their type on every engine. `whereNotIn` with an empty list matches every row. They are `default` methods of `Schema`, so an existing implementation of the interface still compiles.
* **OR and groups.** `Schema#orWhere(...)` (column and value, with an operator, with a table prefix), `#orWhereNull`, `#orWhereNotNull`, `#orWhereIn` and `#orWhereBetween` join a condition to the previous one with `OR`. `Schema#where(group -> ...)` and `#orWhere(group -> ...)` write a group of conditions between parentheses. As in SQL, `AND` is applied before `OR`: `where(a).where(b).orWhere(c)` matches `(a AND b) OR c`. A group without conditions adds nothing. Conditions written without these methods are joined with `AND` exactly as before.
* **Grouping.** `Schema#groupBy(columns...)` and `Schema#having(expression, operator, value)` on selects. The `HAVING` expression is written as is, such as `COUNT(*)` or ``SUM(`amount`)``, and the value is bound; several `having` calls are joined with `AND`.
* **Aggregates.** `RequestHelper#sum`, `#max`, `#min` and `#avg` take a table, a column and the usual conditions, and return a `Number`, or `null` when no row matches. `RequestHelper#exists(table, conditions)` tells whether a row matches without reading it. Like `count`, a failed query returns `null` or `false` unless strict reads are on.
* **Async API.** `AsyncRequestHelper` wraps a `RequestHelper` and returns a `CompletableFuture` from every operation: selects, counts, aggregates, `exists`, writes (completed with the row count or generated key), batches, raw SQL and transactions. A failure completes the future exceptionally with the `DatabaseException`. Pass an `Executor`, such as a server's async scheduler, or let it create a pool of daemon threads (4 by default) that `shutdown()` stops. `RequestHelper` itself is unchanged.
* **Migration rollback.** `Migration#down()` reverts a migration with the same methods as `up()` (`drop`, `modify`, …); it does nothing by default, so existing migrations still compile. `MigrationManager.rollback(connection, logger)` rolls back the last applied migration and `rollback(connection, logger, steps)` the last `steps`, most recent first, following the order the migrations were registered. Each one's `down()` runs and its record is removed, so the next `execute` applies it again. When a migration to roll back has no `down()`, nothing is changed and an `IllegalStateException` is thrown.
* **Migration status.** `MigrationManager.getAppliedMigrations(connection, logger)` returns the names recorded in the migration table, and `getPendingMigrations(connection, logger)` the registered migrations `execute` would apply.
* **Paging.** `Schema#limit(int)` and `Schema#offset(int)` on selects, with the right syntax for each engine (an offset alone works too).
* **Raw SQL.** `RequestHelper#execute(sql, params...)` returns the number of rows changed, and `RequestHelper#query(sql, RowMapper, params...)` maps each row. Both replace `%prefix%` and adapt quoting for the engine.
* **Transactions.** `RequestHelper#inTransaction(tx -> ...)` runs several operations on one connection. It commits when the callback returns and rolls back when it throws. Only calls made through `tx` are part of the transaction.
* **SQLite options.** `SqliteConnection#setJournalMode("WAL")` and `#setBusyTimeout(ms)`.
* **Driver properties.** `DatabaseConfiguration#withProperty(key, value)` adds or replaces a driver property on pooled and plain connections, for example `withProperty("useSSL", "true")` on MySQL or `withProperty("sslmode", "require")` on PostgreSQL.
* **Pool timeouts.** `DatabaseConfiguration#withTimeouts(connectionTimeout, leakDetectionThreshold)`, in milliseconds. `0` disables leak detection, which otherwise warns about any connection held for more than 10 seconds, such as a long transaction.
* **Log levels.** `Logger` has `warn` and `error`, which default to `info` so existing implementations keep working. `JULogger` maps them to `WARNING` and `SEVERE`, and failed operations are now logged with `error`.

### Changes

* `RequestHelper#update`, `#delete`, `#upsert`, `#insert`, `#upsertMultiple`, `#insertMultiple` and `#updateMultiple` keep their `void` signatures, so plugins compiled against an older version keep working. New methods return the result:
  * `#updateAndCount`, `#deleteAndCount`, `#upsertAndCount`, `#upsertMultipleAndCount` and `#updateMultipleAndCount` return the number of rows affected. A conditional update (`where("version", n)`) can tell whether it won.
  * `#insertAndGetKey` and `#insertMultipleAndGetKey` return the generated key (0 when the table has no auto-increment column).
* **Strict reads (opt-in).** `RequestHelper#setStrictReads(true)` makes `#select`, `#selectAll` and `#count` throw `DatabaseException` when the query fails. By default they still log the error and return an empty list or 0, as before. A helper given to `inTransaction` inherits the setting.
* Parameters are bound the same way on every driver: `java.util.Date` is sent as a `Timestamp`, `UUID` and enums as strings.
* An insert no longer fails after writing its row when the driver cannot report generated keys for the table.
* Names and operators written into statements are checked, so they cannot carry SQL of their own. Only what no legitimate value contains is rejected, with an `IllegalArgumentException`: a statement separator (`;`), a comment (`--`, `/*`, or `#` outside a quoted string, which MySQL and MariaDB read as a comment), a string left open, a quote ending a quoted column name, or a `where` operator that is neither comparison symbols nor keywords such as `LIKE`, `NOT LIKE`, `REGEXP` or `IS NOT`. `orderBy`, table names, prefixes and aliases are otherwise written as before.
* The value of `JoinCondition.and(...)` is escaped as a string literal for the engine: quotes are doubled, and on MySQL and MariaDB backslashes are escaped too, so a backslash cannot end the string. `JoinCondition#getJoinClause(Dialect)` writes it for a given engine; without one, backslashes are always escaped.
* MySQL and MariaDB still enable `allowMultiQueries` by default, now as a driver property instead of a URL parameter, so `withProperty("allowMultiQueries", "false")` turns it off.
* `MySqlConnection`, `MariaDbConnection` and `PostgreSqlConnection` open a new connection for each request. They used to share one connection that every request closed, so each query reconnected and two threads could close each other's connection. They use the dialect's URL with the same driver properties as before, plus the configuration's. A connection obtained from `getConnection()` must be closed by the caller.
* `DatabaseConfiguration#toString()` no longer prints the password.

### Fixes

* `Transaction#close()` now releases its connection. A pooled connection used by `beginTransaction()` was never given back to the pool.
* A table prefix containing `$` or `\` no longer breaks `replacePrefix`.
* A batch update run on a connection that is already in a transaction no longer commits that transaction early.
* `whereIn` with an empty list matches nothing instead of producing `IN ()`, which MySQL, MariaDB and PostgreSQL reject.
* `updateMultiple` on MariaDB, whose driver only reports that each statement of a batch succeeded, counts one row per statement instead of 0.
* PostgreSQL inserts return the generated id even when the insert schema does not declare the auto-increment column.
* `MigrationManager.execute` can run more than once in the same JVM (on another database, or the same one again). Each run registered every schema of the migrations again, so the next run created each table and index twice and failed on the index.
* PostgreSQL inserts only ask the driver for auto-increment columns as generated keys. Otherwise the driver returned the whole row and the first column was read as the id.
* On PostgreSQL, `whereIn(column, values...)` binds values with their own type instead of turning them into strings, which PostgreSQL rejects for a numeric column. MySQL, MariaDB and SQLite still receive strings, as before. `WhereCondition#getParameters()` returns the values with their type; `getValues()` still returns strings.
* `addSelect(prefix, column, alias)` and `addSelect(prefix, column, alias, default)` no longer drop the table prefix, which made a column present in both tables of a join ambiguous.
* Selects key each column by its label too, so an alias is a map key on MySQL, whose driver reports the original column name. The original name stays available as before.
* Mapping rows into a class skips `@TransientField`, static and synthetic fields, as writing does, and uses the constructor taking one parameter per mapped field. A class with a transient field used to fail or receive the wrong values. Classes without such a constructor are mapped as before.
* `MigrationManager.execute` throws when it cannot read the migrations table instead of treating it as empty and running every migration again.
* A migration is recorded once, after all of its schemas ran. When one of them failed, the migration was already recorded and the remaining schemas never ran. Adding missing columns to a create-or-alter migration no longer records it a second time.
* `count` reads the count as a `long` instead of an `int`.
* `timestamps()` and `updatedAt()` no longer need `MigrationManager.setDatabaseConfiguration`: the `updated_at` default is taken from the dialect when the table is created.

### Tests

* New tests: `IncrementRequestTest`, `RawQueryAndTransactionTest`, `DialectTest`.
* The whole suite passes on SQLite, PostgreSQL 16, MySQL 8.4 and MariaDB 11.
* The suite runs against a server with `-Dsarah.test.type=POSTGRESQL|MYSQL|MARIADB` and `sarah.test.host`, `port`, `user`, `password`, `database`. It uses SQLite by default.

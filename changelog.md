# Changelog

## Unreleased

### New features

* **PostgreSQL support.** Added `DatabaseType.POSTGRESQL`, `PostgreSqlConnection` and `DatabaseConfiguration.createPostgreSql(...)`. `HikariDatabaseConnection` works with PostgreSQL too. Add the `org.postgresql:postgresql` driver to your plugin.
  * Sarah still writes identifiers between backticks. For PostgreSQL they become double quotes before the statement is sent; text inside `'...'` is not touched. Quoted names are case-sensitive in PostgreSQL, so use a column in the same case everywhere.
  * Types are mapped to their PostgreSQL equivalent: `LONGTEXT` → `TEXT`, `BLOB` → `BYTEA`, `ENUM(...)` → `VARCHAR(255)`, auto-increment → `GENERATED BY DEFAULT AS IDENTITY`.
  * `updated_at` from `timestamps()` defaults to `CURRENT_TIMESTAMP` but is not updated automatically on change, since PostgreSQL has no `ON UPDATE`.
* **Dialects.** The differences between engines moved to `fr.maxlego08.sarah.dialect` (`MySqlDialect`, `MariaDbDialect`, `SqliteDialect`, `PostgreSqlDialect`), available through `DatabaseConfiguration#getDialect()`. `DatabaseConfiguration#prepare(sql)` replaces `%prefix%` and adapts a statement for the configured engine.
* **Atomic increments.** `Schema#increment(column, amount)` adds to a value instead of replacing it:
  * update: `col = col + ?`
  * upsert: inserts the amount into a new row, adds it to the existing value otherwise, in one statement. Two servers adding at the same time no longer overwrite each other.
  * insert: writes the amount as is.
* **Expressions.** `Schema#expression(column, sql, params...)` assigns raw SQL to a column, for example `` `version` + 1 `` or `CURRENT_TIMESTAMP`. On an upsert it only applies when the row already exists.
* **Insert-only columns.** `Schema#insertOnly()` keeps the existing value of the last column when an upsert finds the row, for example a creation date. An upsert where every column is insert-only does nothing on conflict.
* **Paging.** `Schema#limit(int)` and `Schema#offset(int)` on selects, with the right syntax for each engine (an offset alone works too).
* **Raw SQL.** `RequestHelper#execute(sql, params...)` returns the number of rows changed, and `RequestHelper#query(sql, RowMapper, params...)` maps each row. Both replace `%prefix%` and adapt quoting for the engine.
* **Transactions.** `RequestHelper#inTransaction(tx -> ...)` runs several operations on one connection. It commits when the callback returns and rolls back when it throws. Only calls made through `tx` are part of the transaction.
* **SQLite options.** `SqliteConnection#setJournalMode("WAL")` and `#setBusyTimeout(ms)`.

### Changes

* `RequestHelper#update`, `#delete`, `#upsert`, `#upsertMultiple` and `#updateMultiple` return the number of rows affected instead of `void`. A conditional update (`where("version", n)`) can tell whether it won. `#insert` and `#insertMultiple` return the generated key (0 when the table has no auto-increment column). Callers must be recompiled.
* **Breaking:** `RequestHelper#select`, `#selectAll` and `#count` now throw `DatabaseException` when the query fails. They used to log the error and return an empty list or 0, which a caller could mistake for "no data" and then overwrite.
* Parameters are bound the same way on every driver: `java.util.Date` is sent as a `Timestamp`, `UUID` and enums as strings.
* An insert no longer fails after writing its row when the driver cannot report generated keys for the table.

### Fixes

* `Transaction#close()` now releases its connection. A pooled connection used by `beginTransaction()` was never given back to the pool.
* A table prefix containing `$` or `\` no longer breaks `replacePrefix`.
* A batch update run on a connection that is already in a transaction no longer commits that transaction early.
* `whereIn` with an empty list matches nothing instead of producing `IN ()`, which MySQL, MariaDB and PostgreSQL reject.
* `updateMultiple` on MariaDB, whose driver only reports that each statement of a batch succeeded, counts one row per statement instead of 0.
* PostgreSQL inserts return the generated id even when the insert schema does not declare the auto-increment column.
* `MigrationManager.execute` can run more than once in the same JVM (on another database, or the same one again). Each run registered every schema of the migrations again, so the next run created each table and index twice and failed on the index.
* PostgreSQL inserts only ask the driver for auto-increment columns as generated keys. Otherwise the driver returned the whole row and the first column was read as the id.
* `whereIn` binds values with their own type instead of turning them into strings, which PostgreSQL rejects for a numeric column. `Schema#whereIn` now takes a `List<?>` and `WhereCondition#getValues()` returns a `List<Object>`.
* `addSelect(prefix, column, alias)` and `addSelect(prefix, column, alias, default)` no longer drop the table prefix, which made a column present in both tables of a join ambiguous.
* Selects read each column by its label, so an alias is the map key on MySQL too, whose driver reports the original column name.
* Mapping rows into a class skips `@TransientField`, static and synthetic fields, as writing does, and uses the constructor taking one parameter per mapped field instead of the first declared one. A class with a transient field used to fail or receive the wrong values.
* `MigrationManager.execute` throws when it cannot read the migrations table instead of treating it as empty and running every migration again.
* A migration is recorded once, after all of its schemas ran. When one of them failed, the migration was already recorded and the remaining schemas never ran. Adding missing columns to a create-or-alter migration no longer records it a second time.
* `count` reads the count as a `long` instead of an `int`.
* `timestamps()` and `updatedAt()` no longer need `MigrationManager.setDatabaseConfiguration`: the `updated_at` default is taken from the dialect when the table is created.

### Tests

* New tests: `IncrementRequestTest`, `RawQueryAndTransactionTest`, `DialectTest`.
* The whole suite passes on SQLite, PostgreSQL 16, MySQL 8.4 and MariaDB 11.
* The suite runs against a server with `-Dsarah.test.type=POSTGRESQL|MYSQL|MARIADB` and `sarah.test.host`, `port`, `user`, `password`, `database`. It uses SQLite by default.
